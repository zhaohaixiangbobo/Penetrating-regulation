# 营销审计公司级权限控制 — 待办清单

> 目标：让普通用户（`role = user`）只能查询自己被授权的公司数据；管理员（`role = admin`）不受限制，可查全部公司。
>
> 背景：当前 `users` 表无公司字段，JWT 仅含 `username + role`，营销审计接口的 `com_ids` 完全由前端传入、后端只做白名单校验，导致所有登录用户都能查全部 13 个公司数据，存在越权访问风险。
>
> 状态标记：`[ ]` 待办 · `[~]` 进行中 · `[x]` 已完成

---

## 1. 数据库：User 表增加公司关联

- [ ] 方案选型：**单公司** 直接加 `company_id` 字段；**多公司** 建 `user_companies` 关联表（推荐，兼容后续扩展）
- [ ] 修改 `backend/app/models/user.py`
  - 单公司：新增 `company_id: Mapped[str | None]`（对应 StarRocks 的 `com_id`）
  - 多公司：新增 `UserCompany` 模型（`user_id` + `com_id`，联合唯一）
- [ ] 编写迁移脚本 `backend/app/db/migrate.py`（或 `scripts/init_db.py`），为存量用户补齐公司字段/关联记录
- [ ] 校验：`company_id` / `com_id` 必须落在 `app/core/config.py` 的 `VALID_COM_IDS` 白名单内

## 2. 认证：登录时把授权公司写入 JWT

- [ ] `backend/app/api/auth.py` 登录时查询用户授权公司列表，写入 token 的 extra（如 `company_ids`）
- [ ] `backend/app/core/security.py` 确认 `create_access_token` 能承载列表型 claim
- [ ] `backend/app/deps.py`：`Principal` 增加 `company_ids: list[str]` 字段
  - `get_current_principal` 从 JWT 解析出 `company_ids`
  - 可新增便捷属性/方法：admin 返回全部 `VALID_COM_IDS`，user 返回其授权列表
- [ ] `/api/auth/me` 返回体（`MeResponse`）补充 `company_ids`，供前端使用
- [ ] 兼容 OIDC 预留：`auth_provider.exchange_code` 返回体也需带公司信息

## 3. 后端接口：强制公司过滤（核心防越权）

- [ ] `backend/app/api/audit.py` 三个查询接口 + 三个导出接口：
  - 依赖从 `get_current_user` 改为 `get_current_principal`（拿到 role 与 company_ids）
  - **user 角色**：实际查询公司 = `前端传入 com_ids ∩ 用户授权公司`；若交集为空则拒绝或返回空
  - **admin 角色**：不受限，按前端传入的 `com_ids`（仍走白名单校验）
- [ ] `_validate_com_ids` 之后追加"当前用户是否有权访问"的二次校验，越权返回 403
- [ ] SQL 构建（`_build_*_query`）使用**收窄后**的公司列表，不再直接信任前端 `com_ids`
- [ ] `backend/app/api/meta.py`：`/api/meta/companies`、`/api/meta/employees` 也按用户授权过滤（否则员工/公司下拉仍会泄露范围）

- [ ] 导出接口同样覆盖越权场景

---

## 关键原则

1. **后端是唯一权威**：前端过滤只是体验优化，真正的越权拦截必须在后端接口层完成。
2. **收窄而非信任**：user 的查询范围永远是 `前端选择 ∩ 授权公司`，绝不直接采用前端传入值。
3. **admin 不受限**：管理员保持查全部公司的能力。
4. **白名单不可绕过**：所有公司参数仍需先通过 `VALID_COM_IDS` 校验。
