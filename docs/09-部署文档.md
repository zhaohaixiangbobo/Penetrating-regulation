# 穿透式监督查询系统 · 更新部署操作手册

> 本文档面向**日常更新发布**：你在开发机改完代码后，把更新发到已部署的生产服务器需要做的操作。
>
> - **首次全新安装**（装 Python/依赖/Nginx/systemd）不在本文范围，见通用安装说明或《`docs/07-信创服务器部署手册.md`》。
> - 已假设服务器按既有约定部署：代码在 `/opt/shenji`，虚拟环境 `/opt/shenji/venv`，后端由 systemd 服务 `shenji` 守护（127.0.0.1:8000），前端 `dist` 由 Nginx 托管在 `/opt/shenji/frontend/dist`。
> - 仓库地址：`https://github.com/zhaohaixiangbobo/Penetrating-regulation.git`。

---

## 一、更新总流程一图

```
   开发机（Windows）                         生产服务器（Linux）
 ┌────────────────────┐   git push      ┌──────────────────────────┐
 │ 1. 改代码 + 本地自测 │ ──────────────▶ │  GitHub 仓库              │
 │ 2. 前端 npm run build│                 └───────────┬──────────────┘
 │ 3. git commit/push   │      git pull               │
 │ 4. 传 dist（前端改动）│ ───────────────────────────▶│ /opt/shenji
 └────────────────────┘   scp dist                    │
                                                       ▼
                                    5. (依赖变了) pip install
                                    6. systemctl restart shenji  （后端改动）
                                    7. 覆盖 dist + reload nginx   （前端改动）
                                    8. 验证
```

> 关键判断：**改了后端 → 重启 `shenji`；改了前端 → 换 `dist` 并 `reload nginx`；都改 → 两样都做。** 结构/账号/依赖/配置的额外动作见第四节。

## 二、开发机：推送前要做的

### 2.1 后端有改动：先本地自测

```powershell
cd d:\2-code\shenji\backend
D:\3-anaconda\envs\py312\python.exe -m pytest -q        # 跑单元测试
# 或临时起服务手动点：

```

### 2.2 前端有改动：构建产物

```powershell
cd d:\2-code\shenji\frontend

```

### 2.3 提交并推送

```powershell
cd d:\2-code\shenji
git add .
git commit -m "本次更新说明"
git push origin main
```

> `.gitignore` 已排除 `backend/.env`、`backend/data/`、`frontend/dist/`、`node_modules/` 等，`push`/`pull` 都不会动服务器的配置与数据。

## 三、服务器：按“改了什么”执行

登录服务器：`ssh root@<服务器IP>`（更新期间需临时联网以 `git pull` / 装依赖）。

### 场景 A：只改了后端代码

```bash
cd /opt/shenji
git pull origin main
systemctl restart shenji
systemctl status shenji           # active (running) 即正常
```

### 场景 B：只改了前端

```powershell
# 开发机：构建后传输（已在 2.2 构建）
scp -r d:\2-code\shenji\frontend\dist root@<服务器IP>:/opt/shenji-frontend-dist
```

```bash
# 服务器：替换并生效（Nginx 无需重启，reload 即可）
rm -rf /opt/shenji/frontend/dist
mv /opt/shenji-frontend-dist /opt/shenji/frontend/dist
systemctl reload nginx
```

### 场景 C：前后端都改

先做**场景 A**（pull + 重启后端），再做**场景 B**（换 dist + reload nginx）。

## 四、需要额外动作的更新（对号入座）

### 4.1 改了数据库结构（新增表 / 新增字段）

**通常无需手动操作**：后端启动时会自动 `create_all` 建齐新表，并 `ensure_sqlite_schema` 幂等补齐新列。所以场景 A 的 `systemctl restart shenji` 就完成了结构迁移。

如需（重新）确保内置账号或结构，可另跑一次幂等初始化：

```bash
cd /opt/shenji/backend
/opt/shenji/venv/bin/python -m scripts.init_db
```

### 4.2 新增了 Python 依赖（`requirements-server.txt` 变了）

```bash
cd /opt/shenji
git pull origin main
/opt/shenji/venv/bin/pip install -r /opt/shenji/backend/requirements-server.txt
systemctl restart shenji
```

### 4.3 新增了 `.env` 配置项

`.env` 不在 Git 中、不会被 `git pull` 更新。若本次代码新增了配置项，需手动补到服务器的 `.env`：

```bash
vi /opt/shenji/backend/.env      # 参照 backend/.env.example 补上新增项
systemctl restart shenji
```

### 4.4 涉及“审计线索反馈附件上传”（仅首次配置一次）

线索附件单文件上限 10MB，而 **Nginx 默认请求体上限仅 1MB**，会导致上传返回 413。确保站点配置里有（`/etc/nginx/conf.d/shenji.conf` 的 `server` 块内）：

```nginx
client_max_body_size 20m;
```

改完 `nginx -t && systemctl reload nginx`。此项配置一次即可，后续更新无需重复。

> 附件实体存放在 `backend/data/uploads/clues/`，随 `data/` 一起被 `.gitignore` 忽略，`git pull` 不影响，无需处理。

### 4.5 风险模块更新与数据同步（2026-10-02）

按本文的 Git 更新代码、单独传输 `frontend/dist` 方式，**本地运行数据不会自动同步到服务器**。

| 内容 | 部署时的行为 |
| --- | --- |
| 后端代码、指标计算规则、内置模型种子 | 提交并推送后，由服务器 Git 更新 |
| 前端页面 | 构建 dist 后单独上传；dist 包含页面资源，不包含本地 SQLite 记录 |
| 页面新增的模型、草稿/发布版本 | 保存在各环境 SQLite 中，当前无自动同步或模型导入导出功能 |
| 运行记录、证据、预警、核查结论 | 保存在各环境 SQLite 中，当前无自动同步 |
| 原账号、审计线索、全部附件 | `backend/data/` 不通过 Git 更新，服务器保留自己的记录 |
| 开关、数据库连接、密钥 | `.env` 不同步，服务器单独配置 |
| 营销/专卖源数据 | 后端按服务器配置读取 StarRocks；相同数据源和范围下可重新运行，结果还受源数据变化影响 |

服务器首次使用风险模块时，在 `/opt/shenji/backend/.env` 增加或修改以下配置，再重启 `shenji`，更新前端 dist 并刷新页面：

```dotenv
RISK_MODULE_ENABLED=true
RISK_RUN_ENABLED=true
```

后端启动会创建独立风险表；模块启用时幂等初始化内置“拜访履职异常 V1”。**这属于内置初始化，不是把开发机数据库同步过去。** 本地通过页面配置的其他模型及版本（例如“拜访定位偏差 V1/V2”）、运行记录和预警不会随代码自动出现，可在服务器重新配置并运行。

如果需要迁移本地已配置的模型，应先明确只迁移模型配置还是连同运行/证据等记录一起迁移，再做有冲突检查的定向导入。当前没有实现该导入功能；不要用本地 `app.db` 覆盖已有生产数据库，这会同时覆盖服务器账号、线索和风险记录。首次空环境整体迁移需要单独备份及迁移步骤。

以上结论针对本文部署方式。如果改用整目录压缩包或 `scp backend/data`，是否复制数据取决于实际打包/传输内容，`.gitignore` 不会自动约束手动复制。风险附件位于 `backend/data/uploads/risk/`，与原线索附件一并纳入数据备份。

### 4.6 数据库底层表如何更新

服务器更新后端代码并重启 `shenji` 时，`app/main.py` 的启动流程连接服务器自己的 SQLite，先执行 `Base.metadata.create_all`，再执行 `app/db/migrate.py` 中的 `ensure_sqlite_schema`。

1. **新增表**：`create_all` 创建模型声明中尚不存在的表及其索引。本期新增风险模型、版本、运行、证据、预警等独立表通过此方式创建，已有表和数据保留。
2. **已有表改结构**：`create_all` 不会自动给旧表新增/修改字段，也不会自动迁移旧表索引或约束。当前轻量迁移只处理 `users.role`、`users.external_id` 及对应索引。以后已有表变化必须随版本编写可重复执行的迁移与数据回填，并在数据库备份后验证；仅改 ORM 字段定义并重启是不够的。
3. **模型初始配置**：启用风险模块时执行内置模型初始化，与表结构迁移分开；服务器上的用户自建配置由服务器 SQLite 保存。
4. **营销、专卖源表**：本应用读取 StarRocks，不负责修改这些业务表结构或同步其业务数据，更新由原数据平台维护。

2026-10-02 的筛选样式、状态色、线索展示编号和拜访日期展示调整均为前端变化，无需数据库迁移或历史数据回填。更新前端 dist 后刷新页面即可生效。当前尚未引入统一迁移版本账本，后续涉及已有风险表结构变化时需先补齐相应迁移脚本及回退说明。

## 五、账号维护

- 内置账号（`scripts/init_db.py` 预置，幂等）：
  - `admin` / `Tjyc!2026` —— 角色 **admin**（可进入「线索管理」、处理线索、下载任意附件）
  - `user` / `Tjyc!2026` —— 角色 **user**（提交线索、查看「我的线索」、营销审计查询）
- 新增/修正预置账号：编辑 `scripts/init_db.py` 里的 `SEED_USERS` 列表后，服务器 `git pull` 再跑：

  ```bash
  cd /opt/shenji/backend
  /opt/shenji/venv/bin/python -m scripts.init_db
  ```
- 把某个已有账号提升为管理员：在 `SEED_USERS` 中把其角色设为 `admin` 后重跑 `init_db`（幂等会自动修正角色），该账号重新登录后即可见「线索管理」。

## 六、每次更新后的验证清单

- [ ] `systemctl status shenji` 与 `systemctl status nginx` 均为 active (running)
- [ ] `curl http://127.0.0.1:8000/api/health` 返回 `{"status":"ok"}`（直连后端）
- [ ] `curl http://127.0.0.1/api/health` 返回 `{"status":"ok"}`（经 Nginx）
- [ ] 浏览器 `http://<服务器IP>` 能登录，本次改动点功能正常
- [ ] 前端有改动时：**强制刷新（Ctrl+F5）**避免旧缓存；查询页 F5 不 404
- [ ] 涉及附件时：普通用户能上传 > 1MB 文件（验证 `client_max_body_size` 生效）

## 七、回滚（更新出问题时）

```bash
cd /opt/shenji
git log --oneline -n 5            # 找到上一个正常版本的 commit
git reset --hard <上一个正常commit>
# 若依赖有变，回滚后按需重装：pip install -r backend/requirements-server.txt
systemctl restart shenji
```

前端回滚：保留上一版 `dist` 备份，或用对应 commit 重新 `npm run build` 后再传输覆盖。

> 数据安全：回滚只影响代码，`data/`（账号 + 线索 + 附件）与 `.env` 不受影响。重要更新前建议先备份 `backend/data/`（含 `app.db` 与 `uploads/`）。

## 八、常见问题（快速）

| 现象               | 处理                                                                             |
| ------------------ | -------------------------------------------------------------------------------- |
| 前端改了但页面没变 | 浏览器旧缓存。Ctrl+F5 强刷；确认 `dist` 已替换且 `systemctl reload nginx` 执行过 |
| 接口 502/504       | 后端没起。`systemctl status shenji`、`journalctl -u shenji -n 200` 查错          |
| 附件上传 413       | Nginx `client_max_body_size` 未设 20m（见 4.4）                                  |
| 启动报缺某个包     | 依赖没装：`/opt/shenji/venv/bin/pip install -r backend/requirements-server.txt`  |
| `git pull` 冲突    | 服务器不应手改仓库文件；如有本地改动 `git stash` 后再 pull                       |
| 新增配置项不生效   | `.env` 未补新增项（见 4.3），或未重启后端                                        |

## 风险后台服务增量部署（2026-10-07）

API 已取消内嵌运行器，手动试算和正式任务均由独立后台消费。新增入口 `app.risk_worker`，systemd 模板为 `backend/deploy/risk-worker.service`，复用现有依赖，无新增包。

1. 停止旧服务写入，备份 SQLite 及附件。运行中备份应使用 SQLite backup，保留 WAL 一致性。
2. 更新代码及前端 dist，保持 API 与后台使用同一个 SQLite 绝对路径和 `.env`。启动时自动应用 risk_batches_v2 迁移并创建迁移前备份，保留旧预警及证据。
3. 核对模板路径 `/opt/shenji/backend`、解释器 `/opt/shenji/venv/bin/python` 和服务账户；模板沿用既有 root 部署示例，实际按服务器账户调整。复制服务文件至 `/etc/systemd/system/risk-worker.service`，执行 `systemctl daemon-reload`、`systemctl enable --now risk-worker`。
4. 先设置 `RISK_MODULE_ENABLED=true`、`RISK_RUN_ENABLED=true`，保留 `RISK_SCHEDULE_ENABLED=false` 和 `RISK_SOURCE_KEY_VERIFIED=false`，重启 API 与后台后验证小范围试算。
5. 数据维护方确认唯一事件键及更新规则、同步时间后，将源键核实开关设为 true；选择低峰计划，启用调度开关并重启两项服务。开关表示已完成人工核实，不能替代核实。无同步水位时采用回看补偿，界面标注未知。

本地后台启动：在 backend 目录执行 `& 'D:\3-anaconda\envs\py312\python.exe' -m app.risk_worker`。服务器查看 `systemctl status risk-worker`、`journalctl -u risk-worker -n 100`。当前交付未操作生产服务。

配置及运行数据不会随代码自动同步。生产启动迁移只更新表结构和必要回填，不上传本地计划、预警或测试数据。

回退优先关闭计划、停止后台，保留当前数据库。新版本允许同事件在不同模型版本下分别形成事项，旧代码的唯一性假设不再成立，不能直接换回旧执行器。整库恢复会丢失备份之后的核查及证据，应单独确认。测试、源库小样本命令及上线边界见 docs/16-定时计划与自动分批运行方案.md。
