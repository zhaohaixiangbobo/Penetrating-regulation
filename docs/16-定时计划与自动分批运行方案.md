## 1. 建议与范围

建议实现“页面管理定时计划 + 独立后台执行服务 + 自动分批 + 失败批次补跑”。先让现有单次拜访模型稳定自动运行，再扩展月度、客户级等指标。单纯调大 5000 条上限不能解决内存占用、服务重启、进度不可见和失败整段重跑。

第一阶段确定保留 SQLite，采用单机、单后台执行器、计算并发 1。StarRocks 保存和查询业务大数据，SQLite 保存计划、父任务、批次、进度、证据、预警和日志。重点约束 SQLite 并发写与事务持续时间：启用 WAL、使用短写事务，读取 StarRocks 和计算期间释放 SQLite 事务。第一版不引入 Redis、Celery、PostgreSQL；持续锁冲突、多机执行或大量并发写入才触发架构升级评估。证据存储仍需关注磁盘增长和保留周期，不能把“保留 SQLite”理解为不需要容量管理。

### 审批意见落地

确定事项：轻量环境、独立 risk-worker、公司/日期分区、默认约 1000 条且可配置、稳定游标、批次恢复、父任务快照、未知水位如实标注。需要上线前验证的事项：StarRocks 同步时间/水位、单日数据量、SQL 耗时、事件键唯一性及可变性。关键修订：游标与结果原子提交限定为 SQLite 本地事务；计算结果、命中记录与核查事项分层建模，详见第 4.1 节。

本方案不自动开展人工核查、整改、复核、销号；系统只计算并生成待核查预警。定时执行不依赖浏览器打开，也不使用 Codex 的聊天定时任务。

## 3. 用户可见模块和操作

在“风险模型”下新增“定时计划”，保留指标管理、模型管理、运行记录。运行记录增加触发来源（手动/计划/补跑）、计划名称、父任务、批次汇总和失败批次入口，避免把每个批次都铺到主列表。

### 3.1 定时计划页面

筛选：计划名称、模型、启停状态；默认收起高级条件，沿用统一卡片规范。

计划字段：名称、已发布模型版本、公司范围、执行周期、执行时刻、时区、分析日期规则、启用状态、下一次执行、上次结果、创建/修改人。默认固定绑定一个已发布版本；模型发布新版后由管理员明确切换计划，历史任务保存原版本快照。

周期先支持每天、每周指定星期；每月可作为后续，届时需明确短月份和月末规则。页面展示最近五次预计触发时间和分析日期示例，保存前可检查配置。无需向业务用户开放 Cron 表达式。

分析日期规则首先支持“截至昨日，回看 N 天”（例如 N=3，实际值待源同步规律核实）。2026-10-07 的触发覆盖 10-04 至 10-06，按北京时间解释；补跑旧触发时沿用原触发的日期范围，不能重新按当天推算。历史补算采用一次性固定起止日期任务。

操作：新增、编辑、启用/暂停、立即执行、查看运行记录。运行中的任务继续使用创建时的配置快照；暂停计划阻止后续触发，取消本次运行是单独操作。计划执行人记录为系统身份并保留计划创建人及变更日志。

### 3.2 运行记录与进度

父任务显示“待执行/运行中/全部成功/部分失败/失败/取消中/已取消”，并展示成功批次、失败批次、待处理批次、累计扫描、命中、新增预警、已耗时、最近心跳、读取时间范围。完成比例以批次数为准；动态拆分时总批次数变化需明确显示“正在拆分”，不能把扫描行数当成全量百分比。

批次详情显示公司、日期区间、游标页次、尝试次数、扫描/命中数、开始/结束时间、错误摘要。提供“仅补跑失败批次”和“取消剩余任务”；成功结果保留。进度在浏览器刷新、关闭、服务器重启后仍可查询。

## 4. 自动分批与计算一致性

1. 创建父任务时冻结模型/指标版本、判断参数、公司、分析区间、触发时刻、数据读取策略及来源。
2. 当前单次拜访粒度按“一个公司 + 一天”生成逻辑分区；第一版可将批次目标量设为可配置的 1000 条，具体数值经小样本确认。原 5000 条是现有上限，不是经过容量验证的推荐值。
3. 单日超量采用稳定唯一游标分页。`(plan_date, id, in_monthly_plan)` 仅作为现有候选键，须验证完整精度、唯一性、NULL 语义和更新行为；优先使用经数据平台确认的不可变唯一事件 ID，必要时以其作为排序最后一项。游标排序键与业务事件标识分开定义。分页不使用 OFFSET。分页最后一行游标与本批结果在同一个 **SQLite 本地事务** 中提交，详见第 4.2 节；不存在 StarRocks 与 SQLite 的跨库事务。
4. 单批只把有限事件载入内存，完成判断、证据与预警发布后释放内存，随后领取下一批。对比模式的两个版本在同一批证据上计算。
5. 批内保持 SQLite 原子发布。计算结果以 `(parent_run_id, event_key)` 唯一，允许不同父任务及模型版本对同一事件独立重算；核查事项改为版本化去重，详见第 4.1 节。计划触发以 `(schedule_id, scheduled_fire_at)` 唯一，计划修订版本存入快照而不作为放行重复触发的条件，避免触发时改版产生两份任务。分区页次、批次尝试分别设唯一约束。完整重算创建新父任务，补跑是原父任务下新增尝试。
6. 父任务扫描/命中数从成功的最终批次结果汇总，重试失败尝试不相加。客户数/经理数跨批去重统计，不能简单相加。成功批次的预警可先进入台账，详情标注所属父任务尚未完成或部分失败，避免误解为整段已算完。
7. 暂停与取消通过持久化标记在批次领取前和发布前检查；当前已提交批次保留。源查询取消若不能立即终止，页面保持“取消中”，等待查询结束或超时后停止。

粒度边界：公司/日切分仅直接适用于现有单次拜访模型。月度汇总或最近三次事件等模型需声明完整计算分区及上下文窗口，不能把月度数据拆成独立日结果相加后直接判断。

### 4.1 重新计算与预警事项分层

现有代码已允许新运行重新计算同一事件，`risk_run_items` 的唯一键是 `(run_id, event_key)`；当前 `(model_id, event_key)` 位于 `risk_alerts`，约束的是核查事项，而非计算。其实际问题是跨模型版本命中会归入同一事项，难以清晰分开版本语义。本次开发应同时解决版本追溯与每日重算刷屏，不能简单把该约束改成每次运行都新建一条台账。

| 层次 | 唯一边界 | 处理方式 |
| --- | --- | --- |
| 计算结果/证据 | `(parent_run_id, event_key)` | 新父任务可重新计算，保存当次命中、未命中或不可判断及参数快照；同一父任务重试幂等 |
| 批次尝试 | `(batch_id, attempt_no)` | 保存每次尝试状态和错误；仅成功提交的那次计入汇总 |
| 命中关联 | `(alert_id, result_id)` | 每次命中关联本次独立证据，重试不重复插入 |
| 核查事项 | 第一版 `(model_version_id, event_key)` | 同版本重复命中关联已有事项；不同版本命中可形成独立事项并显示历史同事件关联 |

`model_version_id` 必须是不可变版本记录的全局 ID，不能使用多个模型共用的版本号“1”。模型与指标版本、阈值、计算器版本仍冻结到父任务；指标实现变化需要新版本，不能在同一编号下悄悄替换逻辑。

例如同一事件在 V1 的父任务 A、B 中各算一次：保留两份结果、同一 V1 事项；在 V2 的父任务 C 中再次命中：另建 V2 事项并关联 V1 历史。B 若不命中也保留结果供查看，但不自动关闭 A 的核查事项。跨版本重新提示标注为“新版本重算命中”，不直接认定为新的业务事件或风险复发；复发判断需另有真实事件再次发生的依据。

同版本已关闭事项再次被同一事件命中，保留关闭状态与新增命中历史；后续是否开启新核查轮次须有单独业务规则。不要把每日回看重算自动解释为复发。用户主动“重新核查”仍需操作说明和日志。

### 4.2 SQLite 本地事务边界

每批按“领取 → 读源 → 计算 → 提交”执行：

1. SQLite 短事务领取批次，保存租约序号/尝试记录后立即提交，释放会话。
2. 用 StarRocks 连接读本页，关闭读取会话，计算结果；期间不持有 SQLite 写事务，心跳另用独立短事务。
3. 开启 SQLite 短事务，校验租约序号、取消标记与批次状态，批量保存证据、计算结果、命中关联、事项变化、计数和下一游标，标记批次成功后一次提交。尽量用批量 SQL 和预取替代每条事件各发多次 SQL，约束事务时长。
4. 提交前崩溃：本批回滚，重读该页；提交后崩溃：按已保存状态继续下一页，不能重复发布。StarRocks 源数据不会随 SQLite 回滚，重读数据可能变化，须保留尝试时间并适用第 5 节一致性边界。

不得在 SQLite 写事务内等待 StarRocks 查询、网络重试或长时间计算；不尝试分布式两阶段提交。取消与成功提交竞争时，以最终获得本地事务锁并通过校验的状态为准，已经提交的结果保留。

## 5. 源数据变动与漏算处理

当前 StarRocks 查询关联的是现时许可证和员工资料，源系统尚未提供可验证的同步水位。多个批次跨时读取不能承诺获得同一时点全库快照；游标分页也不能解决晚到或排序字段变化导致的遗漏。

第一版应明确采用“运行期间读取、回看窗口补偿”的口径，保存每批读取时间和完整证据。每日回看近 N 天可重新发现晚到记录，预警事项按模型版本及事件标识去重；超出 N 天的更正通过历史补算处理。若源记录因更正变为不命中，已生成预警不自动销号，应记录最新重算结果供人工核查。

上线前由数据平台确认事件键含义及更新规则，并做限定公司/日期的小样本重复键、NULL、跨日重采样检查。小样本未出现重复只能证明样本，不足以证明永久唯一或不可变，仍需源表约束/数据字典/维护方确认。若没有合格键，先选择固定导出快照并分配快照内稳定行号用于分页；快照行号不等于跨快照业务事件 ID。业务标识未落实时，自动正式预警发布不得上线，可先验证快照试算。不得通过拼接当前候选字段或哈希掩盖源数据身份不明确的问题。

如验收要求整次运行严格可复现，必须增加源快照/固定导出批次：冻结原始事实以及相关字典，之后仅对该快照分批计算。快照存储、生成时长及清理策略单独评估。仅保存任务时间或一个自增 ID 上界不足以冻结源更新。

定时点应晚于数据平台实际同步完成时间。若能取得水位，则未达要求时延后并提示；拿不到时页面如实显示水位未知，运行成功不等于源数据完整。

## 6. 调度、失败重试与恢复规则

- 计划存储在数据库。独立调度循环通过租约和唯一触发键生成任务，事务内完成触发记录、队列入库与下一次触发时间推进；进程重启或重复扫描不会重复建任务。
- 同计划存在未结束任务时，将新触发记录为等待，不并行执行；队列须有积压上限，超过时暂停计划并提示管理员，不能无限堆积。
- 停机恢复默认补一个最近到期触发，汇总记录此前遗漏时段；更早范围由管理员显式补算。回看窗口不一定覆盖全部停机期间，页面须展示未覆盖的日期。
- 连接超时等临时错误可限定自动重试（建议初次失败后最多两次，分别等待 1、5 分钟）；配置非法、缺失源主键、歧义事件等数据错误直接失败，等待人工修正。
- 每批记录租约所有者、租约序号、到期时间与心跳；提交必须核对当前序号，旧执行器失联恢复后也不能提交过期结果。接管只恢复过期未完成批次，不修改已成功批次。
- 手动补跑保留批次范围与模型快照；源数据未冻结时标明新的读取时间。自动重试耗尽后父任务为部分失败或失败，管理员仍可补跑。
- 普通暂停不恢复已取消任务；补跑、计划改版、暂停和恢复均保留审计日志。

## 7. 环境需要怎样调整

| 项目 | 第一阶段建议 | 上线前核实 |
| --- | --- | --- |
| API 服务 | 保留现有 Nginx/FastAPI；禁用 API 内嵌运行器 | 实际 systemd 启动参数、进程数量 |
| 后台服务 | 新增一个 systemd 常驻 `risk-worker`，负责调度、查询、串行计算、重试和恢复；调度循环不等待查询完成 | 服务账户、目录权限、开机启动、失败重启、日志轮转 |

| SQLite | 保留现有库，启用并核实 `journal_mode=WAL`；API/后台使用同一绝对路径，连接配置有限写锁等待，短事务、单计算并发 | 本地磁盘、写锁等待、WAL 增长及 checkpoint、备份恢复；WAL 不代表可无限并发写 |
| 网络 | 后台访问现有 StarRocks 内网地址，不新增对外业务端口 | 后台服务账户网络可达、数据源查询额度与超时 |
| 时钟 | 计划显式指定 Asia/Shanghai，落库记录明确时区；主机时间保持同步 | 时区数据可用、服务器时钟与数据平台时钟 |
| 资源 | 初期并发 1、限量分批，后台与 API 设置适当资源约束 | CPU/内存/磁盘余量、日增数据、单批耗时；未取得这些值前不承诺吞吐或硬件规格 |
| 运维 | 页面执行器状态/心跳、失败计数、积压提醒，日志可按父任务/批次检索 | 无须先接短信邮件；后续外部通知单独授权配置 |

API 已移除内嵌执行器；独立入口为 `python -m app.risk_worker`。`RISK_MODULE_ENABLED` 控制模块，`RISK_RUN_ENABLED` 控制计算，`RISK_SCHEDULE_ENABLED` 默认关闭自动调度，`RISK_SOURCE_KEY_VERIFIED` 默认关闭正式发布。API 与后台需使用相同数据库及环境配置。

连接层已配置有限写锁等待，迁移层已启用并验证 WAL。WAL 在迁移/初始化时设置并验证，每个连接设置有限 busy timeout；备份使用 SQLite 一致性备份能力或经过验证的停机备份流程，不能在服务写入中仅复制主库文件而忽略 WAL 内容。批次保留起止时间及失败原因；精细锁等待、提交耗时和长期容量监测作为上线运维核对项，本次未做压力测量。

迁移至 PostgreSQL 或独立队列的触发条件应以多机器需求、持续写锁冲突、吞吐和容量为依据。本地小规模试点无需先完成这类基础设施迁移。

## 8. 数据结构、发布与回退

建议新增计划、计划修订、触发记录、批次和批次尝试表，扩展父运行记录关联计划/触发来源；已有结果明细增加批次归属并保留历史兼容。迁移表记录已应用版本；已有表字段和索引必须用明确迁移脚本，不能只依赖 create_all。

发布步骤：备份数据库与附件 → 应用迁移并验证 → 更新 API（关闭旧内嵌执行）→ 启动独立后台（计划默认暂停）→ 小范围手动分批验证 → 单个计划灰度启用 → 核对队列/预警和页面负载后逐步扩大。待执行旧任务需明确由新执行器兼容消费或先取消，不能直接丢弃。

回退优先暂停计划、停止新领取、等待当前批次终态，再停新后台。兼容版本恢复手工运行，保留新表、已发布结果及日志；旧版若不能识别新父任务，需隔离新队列后再启动旧执行器。数据库整库恢复会覆盖发布后新增核查记录，因此只能作为单独确认的数据恢复操作。
