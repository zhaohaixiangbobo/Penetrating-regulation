## 4. 对象、指标和模型定义

### 4.1 四个独立概念

| 概念 | 一期例子 | 约束 |
| --- | --- | --- |
| 评价单元 | 一次拜访事件 | 两项条件必须绑定同一事件 |
| 关联主体 | 零售户、客户经理、所属单位 | 使用业务 ID，姓名和机关简称仅作展示 |
| 观察范围 | 所选开始日到结束日 | 包含结束日，界定本次计算范围 |
| 核查事项 | 某模型下的一次异常拜访 | 一期保持事件级，不按滚动 30 天自动合并 |

已核对源表复合键为 `(id, plan_date, in_monthly_plan)`，其中 `in_monthly_plan` 允许 NULL。实际事件键为三字段的 JSON 数组，NULL 原样保留；客户或经理姓名不参与标识。源 ID/时间缺失、事件键重复或人员跨公司关联歧义时整次运行失败，提示先核实源数据；许可证关联缺失/不唯一时距离指标不可判断。

### 4.2 指标定义与条件分离

| 指标代码 | 指标名称 | 原始值/单位 | 数据前提 |
| --- | --- | --- | --- |
| `visit_duration_seconds` | 拜访时长 | 秒，保留原始精度 | 有效拜访，时长含义及缺失/负值处理确认 |
| `visit_location_distance_meters` | 签到与经营地址距离 | 米，保留原始精度 | 坐标范围与来源明确、两端坐标可计算 |

指标版本记录数据源、公式、适用对象、单位、数据质量规则和计算逻辑版本，不固定模型阈值。模型版本中的条件引用指标版本，配置比较运算和阈值。

默认模型条件：

```json
{
  "evaluation_unit": "visit_event",
  "combination": "ALL",
  "conditions": [
    {"indicator": "visit_duration_seconds", "version": 1, "operator": "lt", "value": 60},
    {"indicator": "visit_location_distance_meters", "version": 1, "operator": "gt", "value": 200}
  ],
  "minimum": 1
}
```

指标计算器由开发实现并注册白名单，界面支持选择已有计算器及参数，不开放直接执行任意 SQL/Python。原查询里的阈值下拉属于临时查询，与发布模型的正式参数独立。

### 4.3 条件判断及缺失值

每个条件返回命中、不命中、不可判断三种结果。

- ALL：出现不命中则整体不命中；全部命中才命中；其余不可判断。
- ANY：有一个命中即命中；全部不命中才不命中；其余不可判断。
- AT_LEAST_N：已命中数达到 N 则命中；命中数与未知数之和仍不足 N 则不命中；其余不可判断。

N 满足 `1 <= N <= 条件数`。数值参数统一单位后比较，禁止先将距离四舍五入再判断。不可判断记录单独计数，并在命中证据中保留未知条件，不能宣称所有数据完整。

一期允许平面条件组合，不开放跨粒度嵌套。重复条件拒绝保存；同一指标的包含条件或互斥条件进行语义校验，AT_LEAST_N 中同一指标多条件的重叠计数一期限制使用。至少命中 N 项代表逻辑匹配，不自动代表 N 个独立风险来源，也不自动提升风险等级。

比较字段：命中事件数、涉及客户数、涉及经理数、相对基准新增事件数、减少事件数、共同事件数、不可计算数。点开新增/减少查看实际记录，不将“涉及对象总数”标为“新增对象”。

试算不会证明模型准确性，核查结论才提供效果反馈。

### 5.4 运行记录

运行记录保存 ID、模型版本、模式、触发人、范围、配置/基准快照、开始结束、阶段、取消请求、错误和计数。页面展示主要字段及：扫描数、命中数、不可判断数、指标资料不足数、客户数、经理数、新增/已有预警、已关闭旧事件重命中；对比额外展示基准命中、新增、减少、共同命中。源同步水位明确显示未知。

### 5.5 台账和证据详情

台账显示预警号、模型、公司、客户、许可证、经理、事件时间和状态；详情展示首次/最近发现时间、首次版本、结论、相关历史及每次判定快照。

详情包含四部分：

1. 预警概况：场景、评价对象、处理状态；一期尚未配置核查优先级。
2. 判断依据：实际指标值、比较运算、阈值、条件命中结果、组合结果和质量提示。
3. 时间线：本事件发现和核查过程；相关历史事件明确标记为背景，不冒充本次组合依据。
4. 原始证据：源记录键、必要字段快照、对应运行数据版本、源详情入口或只读详情抽屉。

若同一事件被不同模型版本再次判定，保留每次判定及参数，历史详情不替换成当前模型条件。

### 5.6 看板

一期显示：全量试点事项的待核查、核查中、待整改、待复核、已关闭及失败运行数；最近 30 个有发现记录的日期趋势、模型预警分布、当前核查结论分布、已关闭事项确认问题率。暂无期间筛选和单位分布，相关能力后续扩展。

业务异常趋势按发生时间，新增预警趋势按发现时间；历史回算单独标记。确认问题率以选定预警队列中已完成核查的数量为分母，展示已核查/未核查数及结论分布，证据不足不作为正常。单位比较必须同时考虑业务量和可计算覆盖率。

## 6. 运行机制与任务可靠性

一期手动触发后台任务，接口及时返回运行 ID；前端按需读取进度。默认单运行器顺序处理，限制同时运行数量，避免在线查询与批量运算互相影响。不引入新依赖作为默认前提，如确需安装包，先列明用途由用户安装。

任务状态：`queued → running → succeeded / failed / cancelled`。运行进度与正式生效分开：

1. 写入运行记录并固定模型、指标版本、参数和授权范围。
2. 一期单批限量读取 StarRocks，只读计算；单次最多 31 天、5000 次拜访。读取 5001 条即拒绝发布并提示缩小范围，结果不会被静默截断。
3. 失败或取消保留失败信息，候选结果不进入正式台账和正式统计。
4. 正式运行完成后，执行幂等归并；同一事务内确认归并完成及运行成功，避免半批数据误作完整结果。
5. 大规模数据需另行设计分阶段提交和发布标志，一期限制运行范围，防止长事务影响 SQLite。

运行器已使用 SQLite 单实例租约、4 秒心跳和租约失效校验；过期工作进程不能继续提交。服务重启取得租约后将中断任务标记失败；短暂数据库故障会记录日志并重启取任务循环。失败后在模型管理选择同版本及范围重新运行，生成独立运行记录；一期没有一键重试按钮和 retry_of 字段。

取消以任务检查点协作停止为准。停用开关或停止任务后需确认运行器已停止提交，不能仅在浏览器隐藏按钮。

数据截止不能用任务启动时刻代替。两系统分别记录已确认的同步水位；源系统无法提供水位时明确未知。关键快照只能证明实际读取的证据，无法凭空提供源库事务快照保证。

后续定时运行复用同一任务入口和幂等逻辑，调度另行启用。正式任务不会因用户保持页面打开而运行。

## 7. 去重、版本变化和复发

### 7.1 一期事件级去重

建议预警稳定键为“模型家族 ID＋已验证的源事件键”，不包含 run_id，也不直接包含模型版本。每次运行的命中保存独立 occurrence，通过关联表指向同一预警。

同一事件多次执行仅补充判定关联，不增加独立事件数。页面支持按客户名称、许可证号和状态筛选，详情列出同客户及经理的相关历史事件；一期未实现经理分组列表。未来自动聚合采用独立 case 层，不覆盖事件层数据。

### 7.2 再次命中的分类

| 情形 | 行为 |
| --- | --- |
| 未关闭事件再次计算命中 | 关联新运行记录，保留原核查历史 |
| 已关闭旧事件重跑命中 | 保持关闭，不算复发 |
| 旧事件出现新证据 | 保留每次命中快照，由管理员根据证据选择重新核查并留日志；自动差异提醒后续实现 |
| 参数变化导致历史记录首次命中 | 保存实际参数版本及发现时间；专门的“历史发现”标签后续实现 |
| 关闭后发生新的同类事件 | 新建预警，关联历史事项，标记再次出现 |
| 历史确认问题并完成整改，之后发生同类新事件 | 标记疑似复发；单独“确认复发”结论和统计后续实现 |

未再次命中不自动销号，模型停用不关闭事项，源数据删除不删除已保存证据。历史为合理情形的事项不能作为“已确认问题”的复发依据。

## 8. 核查处置及线索关联

流程状态建议：待核查、核查中、待整改、待复核、已关闭。结论另设字段：确认问题、合理业务情形、数据质量问题、证据不足、核实正常。“其他”仅在有补充分类和说明时使用，不作为默认选项。

主要流转：

- 待核查 → 核查中：记录核查人和开始时间。
- 核查中 → 待整改：确认问题，记录事实与处置要求。
- 待整改 → 待复核：提交整改说明及证据。
- 核查中 → 待复核：合理情形、核实正常等结论附依据。
- 待复核 → 已关闭或退回：记录复核人与意见；正式使用时核查与复核身份分离。
- 证据不足保留补证要求，不直接生成正常标签；数据质量问题记录修正责任与复查安排。

所有状态变更通过后端校验，并使用记录版本/条件更新防止并发覆盖。处理日志追加保存，不覆盖旧意见。附件复用现有安全处理原则，权限跟随所关联预警。

审计线索仍是人工入口，风险预警是系统输出。新增多对多关联，不修改原线索主键或把旧线索迁移成预警。查看关联项时重新执行目标项权限校验。

统一前缀 `/api/risk`：

实际文件：`backend/app/api/risk.py`、`schemas/risk.py`、`models/risk.py`、`services/risk_rules.py`、`services/risk_engine.py`。前端为 `services/risk.ts`、`pages/Risk/{Indicators,Models,Runs,Alerts,Dashboard}.tsx`、`components/RiskClueLinks.tsx`。测试集中在 `backend/tests/test_risk.py` 和 `manual_risk_smoke.py`。

## 11. 功能开关与权限

已增加两个独立后端开关，配置位于 `backend/.env`，修改后重启后端生效：

- `RISK_MODULE_ENABLED`：新模块页面入口及 API 是否启用，默认关闭。
- `RISK_RUN_ENABLED`：是否接受新的试算/正式任务，默认关闭。
- 自动调度尚未实现，无 `RISK_SCHEDULER_ENABLED` 配置项。

前端读取后端能力配置控制菜单，后端接口仍须独立拦截，不能仅隐藏菜单。开关的配置来源、修改权限及生效方式在实现中明确；一期可采用修改配置并重启服务，不能宣传成已实现热更新。

第一轮试点默认仅管理员访问。开放普通用户前完成风险模块公司—机关范围授权，覆盖查询、运行、详情、导出和关联线索；不能把旧接口仅登录校验的现状继承为新模块授权方案。

当前上述操作仅管理员可以访问；后端强制核查人与复核人不同。一人管理员环境可以运行和核查，最终复核须由另一名实际管理员完成。没有为方便演示绕过复核校验；角色与单位范围细化属于正式推广前的工作。

## 12. 分阶段开发和检查点

| 阶段 | 内容 | 阶段出口 | 回退边界 |
| --- | --- | --- | --- |
| 0 基线准备 | 代码基线、配置/数据库/附件/构建产物备份，明确源键和坐标口径 | 恢复演练及基线清单 | 完全保留原系统 |

| 2 试算与运行 | 后台任务、进度、同批次参数比较、失败取消 | 小范围真实数据与原 SQL 对照 | 保留试算数据，停止新任务 |
| 3 正式预警 | 发布/正式运行、事件去重、证据详情 | 重跑不重复、历史参数可追溯 | 关闭模块，保留新增表 |
| 4 核查与看板 | 分类结论、日志、复核、线索关联、简版统计 | 一条完整业务闭环、权限验收 | 保留核查记录，恢复原入口 |

建议开发分支采用 `codex/risk-model-v1`；如果已存在适用分支则核查后复用。分阶段形成独立提交并记录提交哈希，验收节点保存兼容的前后端产物。每阶段先可操作展示再继续扩大，不一次性大改全部页面。

开发工期需要在数据键、运行量和权限范围确认后估算。单项预计超过 10 分钟的执行先说明耗时及进度方式；超过 30 分钟的批量任务按用户约定确认后启动。

## 13. 回退设计与操作规程

### 13.1 开发前备份清单

| 内容 | 保存方式与验证 |
| --- | --- |
| 代码 | 核实完整提交哈希、工作区改动，建立基线引用；未提交内容先单独保存 |
| 前端产物 | 保存已验证的部署目录/压缩包与版本清单，包含静态资源 |
| 后端与依赖 | 保存部署代码、依赖清单、运行启动方式；新增依赖单独记录 |
| 配置 | 单独安全备份实际环境文件及服务/Nginx配置，禁止提交密码到 Git |
| SQLite | 使用数据库一致性备份方式；有持续写入时使用 SQLite 备份接口或停写后备份，不能只复制正在写入的主文件而遗漏 WAL |
| 附件 | 按实际配置路径备份，与数据库备份批次对应 |
| 清单 | 记录备份时间、路径、大小/校验值、代码版本和恢复验证结果 |

本次本地备份位置和验证见第 16 节；备份位于被 Git 忽略的数据目录。正式部署前还应复制到独立备份介质，避免连同整个工作区一起被覆盖。数据库和附件应按同批次保留。

### 13.2 一级回退：关闭新功能

适用：不喜欢交互、暂不使用、暂停试点。

1. 禁止新运行，停止自动调度（如后续已启用）。
2. 等待或协作取消执行中任务，确认运行器停止写入。
3. 关闭风险模块开关，使新接口停止服务、新菜单隐藏；按实现约定重启应用。
4. 验证旧查询、导出、登录、线索反馈正常。
5. 保留配置版本、预警、证据和核查数据，后续可以重新启用。

此方式不需要恢复数据库，不会主动丢弃升级后的账号/线索记录。新模块数据库表仍保留。

### 13.3 二级回退：切回上一版代码和产物

适用：新版本影响原功能，或决定撤回开发。

1. 执行停任务、停写检查，并备份当前运行数据及部署状态。
2. 部署经过验证的旧后端代码和对应前端产物，恢复必要配置。
3. 保留当前数据库和附件，利用新增表兼容旧代码的设计继续运行原功能。
4. 检查旧应用启动、登录、七项查询中的代表案例、导出、线索和附件。
5. 留存本次回退记录及新模块数据，不自动删除表或文件。

采用独立新增表、关联表和独立配置，避免重命名/删除旧列、改写旧状态枚举或强制搬迁旧数据。若某阶段必须进行不兼容迁移，该阶段需先单独提出迁移与恢复方案，不能继续沿用“可直接回切”的承诺。

不将 `git reset --hard` 或 `git clean` 作为默认回退方法。优先部署旧版本产物，开发分支通过限定提交撤销或保留当前工作后切换；对后续独立修改进行保留，不能一并回退。

### 13.4 三级恢复：数据库或附件恢复备份

适用：确认发生数据损坏或不兼容变更，前两种回退不能解决。

恢复旧备份会回退备份之后的账号、线索、预警和核查记录，必须先列出影响时间段及对象，保存当前数据，并由用户明确确认恢复范围。优先评估选择性修复/迁移，整库恢复作为最后手段。

数据库和附件按一致批次恢复，在停写状态完成；恢复后校验完整性、记录数、登录、附件可读及抽样业务记录。必要时对备份后新增的原系统业务记录执行单独对账与恢复，不能只保证代码启动成功。

### 13.5 回退验收标准

- 风险任务全部停止，刷新页面也不会触发遗留任务。
- 原入口可用，前后端版本匹配，无残留资源 404。
- 既有查询筛选、分页及至少一个导出样本可用。
- 既有线索、处理日志和附件保留，权限行为正常。
- 新预警数据按约定保留；涉及恢复旧数据时，影响清单得到确认。
- 记录回退原因、时间、执行人、代码与备份版本、验收结果。

### 16.1 页面与使用步骤

1. 管理员登录，进入“风险模型 → 指标管理”查看时长、距离定义。

4. 试算或运行时选择公司和日期；“运行记录”自动打开本次详情，后台执行与浏览器保持打开无关。查询超过限额会明确失败，应缩小范围。
5. 对比选择同模型的另一个版本为基准；点击“相对基准新增/减少”查看事件差集。
6. 正式运行命中进入“风险预警 → 预警台账”。详情内查看指标值、阈值、来源坐标、历史判定、相关历史，再填写核查处置、上传附件或关联原审计线索编号。

8. “风险分析 → 风险看板”读取台账实际状态和结论。命中仅表示需要核查，数据不会自动变成确认问题。
