# 风险穿透预警体系分阶段建设建议（讨论稿）

编制日期：2026-10-01。

依据：用户提供的《风险穿透预警体系建设与系统扩展方案.docx》，以及当前工作区的查询接口、页面、线索反馈模型和开发文档。本文是建议方案，本轮仅新增此文档，不修改业务代码、不启动预警任务、不更改原 Word 文件。原文提到的 36 项属于需求范围，本轮实际确认已经实现的业务查询为 7 项；其余需求与数据可用性须另外核实。

## 一、总体判断与建议目标

原方案提出的“查询—指标—场景—预警—核查反馈”方向可采用。当前最值得建设的是统一指标口径、可复现的证据和最小核查闭环。现有技术和七项查询可以支撑第一轮试点，距离完整的“6+1”模型体系仍有数据、历史状态和核查机制的缺口。

建议将“6+1”明确为总体路线，将近期交付范围收敛为：

1. 七项既有查询继续保留，沉淀为有编号、版本、对象粒度和证据来源的规则目录。
2. 建设两类场景试点：拜访履职异常、客户服务覆盖异常。
3. 将扣款户名不符作为经营主体信息一致性的单项预警，积累核查依据后再扩展为经营状态一致性模型。
4. 配套统一预警台账、证据详情、核查结论和简版看板，跑通一轮业务闭环。
5. 后续按数据就绪情况扩展订货、专卖检查、案件，再评估语义分析及学习排序。

“模型”在第一阶段指可解释的场景规则组合，并不要求训练算法。风险等级表达核查优先级，命中规则不能直接认定违规，也不应直接用作人员考核结论。

### 指标计算原则

- 保留“源系统有效记录”（例如状态 03）与“经核查可信记录”两个概念。命中短时长、定位偏差后，不能未经核查就把该记录从所有有效拜访统计中删除。
- 30 日短拜访率 = 短拜访记录数 / 同窗口可计算时长的有效拜访记录数；同时展示分子、分母、缺失时长数。
- 30 日定位偏差率 = 偏差记录数 / 同窗口两端坐标通过质量检查的有效拜访记录数；同时展示坐标可计算覆盖率。
- 综合异常拜访率 = 命中任一已启用拜访规则的去重拜访数 / 同口径有效拜访数。分母中的部分记录若无法计算某项规则，应同时展示覆盖率，避免解读为全部正常。
- 应访未访率 = 达到统计截止条件仍未完成要求的客户数 / 该期间有服务义务的客户数。多种客户身份先统一服务义务，避免同一客户重复计数。
- 分母为零、关键字段缺失、数据未同步，应分别标记为“不适用”“不可计算”“待数据齐备”，不能一律记为 0 或正常。
- 连续异常在同一经理—客户关系的全部适用拜访记录序列上判断，正常记录会打断连续性；不能先过滤异常再计算连续次数。
- 人员异常率配套样本量和同类任务背景；样本太少时仅展示事实，暂不排名。最低样本量在试点分布和人工核查后确定。

## 四、现有查询需要优先完善的业务口径

### 1. 缺访：从评价生效月升级为服务义务月历

目前两项缺访取评价记录的生效月，并未完整展开客户在持续有效期间每个月的应访义务。建议形成“客户类型有效期×月份×服务要求”，先计算应访，再关联实际拜访。

需要确认：月中加入或退出是否需要拜访、同月多次类型变更如何处理、当月是否只做进度提示。未到截止日的本月零拜访建议标为进度关注，正式缺访在业务截止和数据同步完成后形成。

全商品缺访目前用最早许可证变更月作后续排除，会把停业后恢复经营的客户持续排除；变更当月整体排除也可能掩盖此前仍存在的服务义务。自动采集户的例外处理尚未与全商品统一。应建设停业、复业、注销等事件有效期，按适用日期计算义务，而不是仅保存最早停业日期。

### 2. 日拜访不足：补齐没有记录的日期

按拜访表分组只能找出有记录但累计不足的情况。要覆盖完全未拜访，应由在岗经理名册、人员任职有效期和工作/任务日历生成经理—日期基表，再左关联拜访。

不能把每个自然日都作为应拜访日，也不能把当前负责经理自动套用到历史月份。

### 3. 定位偏差：先解决坐标质量与时点匹配

确定两系统坐标系、坐标精度及经营地址来源。将无法计算、明显无效的坐标独立统计为数据质量问题；超过阈值只代表需要核实的空间偏差。

历史拜访应尽可能匹配当时有效的经营地址。仅有当前地址时，记录该限制，不能把搬迁造成的历史偏差直接认定为异常履职。现有展示的“两位小数”只用于阅读，阈值判断保留原始距离。

### 4. 户名不符：从文字比较扩展到身份核对

当前以 `manager_name` 和最新绑卡户名比较，没有核实所有主体是否适用“同名”要求。建议补充主体类型、法人字段和可核验的授权关系；合理例外必须有依据、适用范围和有效期。

`sysupdatedt` 的业务含义需核实，它目前被作为绑定时间展示，但字段名本身只能表明更新时间。原方案如涉及“解绑/换绑发生时间”，应另取对应业务事件。

相同更新时间下多条绑卡记录，当前使用 UUID 稳定选一条；稳定选择不等于真实业务先后，必要时列为数据待核实。姓名 NULL、纯空格等应独立形成完整性提示，避免被误认为比对通过。

### 5. 机构、客户与历史归属统一

营销公司代码与专卖发证机关代码建立显式映射，展示简称仅用于阅读。许可证号保留前导零，以对象映射表连接客户 UUID、许可证内部 ID、历史许可证号和人员 UUID；一对多关联要有明确保留或去重规则。

近期可以先覆盖零售户、客户经理、拜访事件三个实体，再按数据就绪程度扩展检查人员和案件，避免空建对象体系。

## 五、近期可建设的场景模型

### M01 拜访履职异常场景：优先试点

输入：V01、V02、V03、G01及重复发生特征。

建议逻辑：

- 单项短时长、超长或定位偏差，形成一般关注事实。
- 同一拜访 ID 同时短时长与定位偏差，进入组合风险候选。
- 同一经理—客户在观察窗内多次出现同类组合异常，提高核查优先级。
- 人员整体异常率与日工作量作为补充背景，与单次事件分层展示。

原方案中的“连续 3 次”可以作为待校准试点参数，不能直接表述为已批准标准。超长与极短属于同一时长维度；同一事件的多项规则、同一规则的次数和比例，不能当作互相独立的多份证据累计加级。

例：同一记录 38 秒且偏离 438 米，可生成包含两项事实的待核查线索；另一时间发生的 38 秒与 438 米，应分别记录，不能拼成同一次拜访。

### M02 客户服务覆盖异常场景：义务月历完成后试点

输入：客户类型有效期、服务频次、经营状态、实际拜访、任职归属。

统一输出客户—月份的应访次数、实际次数、差额、适用天数、排除原因。闭月后应访未访进入核查；连续月份缺访或长期未服务提高优先级。

S01、S02由共同服务义务规则驱动，仍保留原查询入口。两个客户类型同时命中时，一个对象月份可携带多项义务证据，但预警台账需要去重。

### M03 经营主体信息一致性场景：先保留单项预警

近期只有 C01 的信息较完整，可以先建立姓名差异证据和核查反馈。G01主要服务拜访履职判断，不宜仅凭签到偏差推定零售户经营状态异常。

待接入订单、许可证历史状态及档位变更后，扩展“停注销期间仍有订单”“跨系统档位不一致”等规则，再形成原方案中的经营状态一致性场景。

### “6+1”的后续就绪条件

| 场景 | 前置条件 | 推荐安排 |
| --- | --- | --- |
| 拜访履职真实性 | 拜访事实、坐标质量、相同事件对齐 | 近期先以“拜访履职异常”试点 |
| 服务履职完整性 | 服务制度、客户类型/经营状态有效期、义务月历 | 近期第二个场景 |
| 经营状态一致性 | 身份关系、状态历史、订单与档位数据 | 户名单项先行，逐项扩展 |
| 异常经营行为 | 可比口径的订单、供货限制、季节/节假日、同类群组 | 数据验证后建设 |
| 专卖检查质量 | 检查事实、任务、时长、结果、照片及权限 | 独立试点，再关联营销 |
| 案件办理一致性 | 案件主键、各环节版本、金额数量口径、流转台账 | 独立试点，明确流程阶段 |
| 综合穿透 | 已验证的场景、统一对象与时间窗、关联证据 | 先做综合画像与核查清单，再评估综合排序 |

## 六、建议补齐的体系结构

### 1. 指标与参数管理

每项指标保存：编号、名称、对象粒度、适用对象、数据源、时间字段、计算公式、分母、单位、缺失处理、排除条件、阈值依据、生效期、运行周期、负责人、版本、证据字段。

页面临时选择“280 分钟”属于探索查询；正式任务使用已发布策略版本。参数修改记录来源、原因和生效时间，新旧结果保留版本，历史重算另起批次。将现有查询 SQL 抽取为可复用、可校验的逻辑，优先只预计算高复用或计算成本较高的特征。

### 2. 计算与结果留存

建议保留三类记录：指标事实、场景命中、预警事件。每次计算记录批次号、逻辑版本、参数版本、数据截止时间、源表更新水位、成功/失败和行数。

日规则在数据到齐后运行；月规则按业务截止与迟到数据容忍期运行。频率由数据同步节奏决定。失败显示失败，不能将失败结果覆盖为“无风险”；新增迟到数据时支持限定范围重算。

同一对象、场景、业务事件或统计期建立稳定预警键。同批次重跑幂等，持续命中更新既有事件及证据，新增规则版本保留结果关联，防止每天重复建单。已销号后新事件再次发生标为复发；同一旧事件重算不能直接算复发。

证据保存源记录 ID、业务时间、必要字段快照和计算值，详情提供查询入口。仅保留一个实时查询链接不够：源数据被修改后，应仍可解释当时为什么预警。

### 3. 核查闭环提前进入一期

复用现有线索、附件和处理日志，增加预警关联与核查字段。建议将两个维度分开：

- 流程状态：待核查、核查中、待整改、待复核、已关闭。
- 核查结论：确认问题、合理例外、数据质量问题、证据不足、核实正常。

确认问题进入整改与复核；合理例外、核实正常经复核可关闭；数据质量问题生成数据治理任务；证据不足标记补证或暂缓，不作为“正常”标签。保留结论依据、核查时间、责任人、例外有效期、复核意见及重新打开记录。

### 4. 权限与组织责任

现有营销专卖接口主要做登录校验，现有公司级权限文档仍是待办。正式预警上线前应补齐公司—机关映射与授权范围，后端统一作用于列表、详情、原始证据、附件、导出和统计。人员履职预警由授权人员核查；参数发布、任务执行、复核和核查操作保留审计记录。

## 七、页面如何演进

保留“营销审计”“营销专卖”入口，避免一次性改动全部菜单。近期增加或完善：

| 页面 | 近期交付内容 |
| --- | --- |
| 指标目录 | 七项规则定义、参数来源、口径、版本、数据质量及最近运行结果 |
| 预警台账 | 对象、场景、等级、发现/业务时间、处理状态、命中事实；筛选后穿透 |
| 证据详情 | 指标值与阈值、相同事件关联、数据截止时间、证据快照、源记录入口 |
| 核查反馈 | 复用线索功能，补结论分类、预警关联、整改复核和关闭 |

看板同时区分“命中规则条数”“去重事件数”“涉及客户/经理数”“人工确认问题数”。预警趋势按发现时间，业务异常趋势按发生时间，历史回补单独标识。将核查优先队列与员工绩效评价分开。

## 八、对原方案的具体修改建议

| 原方案位置或观点 | 建议修改 | 理由 |
| --- | --- | --- |
| 一期建设“6+1”，同时涉及案件和语义识别 | 改为总体目标；近期为七项指标目录、两类场景、户名单项及闭环 | 当前数据和功能支撑程度不同，避免以模型名称代替可验收能力 |
| 实施顺序中闭环排在大模型之后 | 将最小闭环与第一批预警同步建设 | 需要尽早发现误报原因、积累可信反馈 |
| 把许可证号作为重要主键 | 使用统一对象 ID 与业务键历史映射 | 许可证变更、重复/缺失及跨系统一对多关系需要承接 |
| 第一阶段优先建设中间四层 | 增加运行治理、结果持久化、权限及反馈的最小范围 | 指标能计算不等于可以持续稳定预警 |
| 多信号共同出现提高风险 | 明确事件 ID、时间窗和维度相关性 | 避免不同事件误拼证据、相似指标重复加级 |
| 用当前字段判断历史风险 | 落实业务状态、经营地址、任职归属有效期 | 原文已提出状态有效期，应扩展到所有会变化的关联属性 |
| “查获数量≠入库数量≠当前库存” | 改为同阶段应交接数量核对，以及期初+入库−出库±调整=期末 | 正常出库、销毁或移交就会造成库存与查获量不同，简单不等式易误报 |
| 第一阶段指定本地 Qwen32B | 改为可替换的本地语义服务；型号、资源及效果完成评估后确定 | 当前未核实部署资源和语料，业务先明确输入输出与证据要求 |
| 预警解释必须经大模型生成 | 确定性指标先用模板解释，复杂文本再引入语义服务 | 模板即可保证数值、时间窗、来源与结果一致 |
| 核查反馈直接成为训练标签 | 增加复核质量、标签时间、抽样策略及未知状态 | 未核查和证据不足均不能当作正常；规则挑选的样本也不代表总体 |
| 论文评价使用 PR-AUC、Recall@K 等 | 补充代表性评估样本、未命中对象抽查和时间外验证 | 只核查预警样本无法可靠估计总体漏报或召回 |

原方案中“先使用可解释规则”“业务历史状态”“硬规则与组合触发分开”“大模型提取证据、人工作结论”可继续保留。硬规则需有明确适用范围和可靠数据；所谓直接触发是直接进入待核查，不是直接确认问题。

## 九、模型效果与研究数据如何留

近期先记录可解释的运营指标：

- 可计算覆盖率：可计算对象数 / 适用对象数，按指标分别统计。
- 异常命中率：命中对象数 / 可计算对象数，统一统计粒度。
- 确认问题率：确认问题数 / 已完成核查数，保留结论分类分布和待补证数。
- 核查及时率：规定期限内完成核查数 / 本期到期应核查数；期限按业务要求配置。
- 无效重复预警率、数据问题占比、平均核查耗时和销号后复发情况。

比较阈值时，应在同一数据快照、同一对象群体和相同标签集合上重放。高风险重点核查之外，抽取少量未预警对象进行复核，逐步评估遗漏情况。抽样量依据业务承载能力制定，不在缺少数据分布时给出固定命中率承诺。

后续研究保留规则向量、原始特征、模型版本、当时可获得的信息和核查结论。训练/评估按时间划分，并检查同一客户、案件或重复事件跨集合的信息泄漏；避免把未来处罚或后续核查结论当作当时输入。

先与现行单规则、组合规则比较，再考虑原方案提到的学习排序或分类。是否采用算法取决于真实核查效果和成本改善。语义服务试点需人工标注小样本、原文定位、抽取字段结构、不能判断选项及版本留存；文书内容作为数据处理，不得触发系统操作。

## 十、实施次序、交付物与验收门槛

| 阶段 | 工作范围 | 可验收交付 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| A 口径与数据审查 | 核实七项规则、业务键、坐标、服务义务、状态及权限 | 指标口径表、字段映射、数据问题清单、可重复的少量样本案例 | 负责人确认适用范围、阈值来源、关键未知项的处理方式 |
| B 最小预警闭环 | 优先 V01/V02/G01、C01；建设运行批次、证据、台账、反馈 | 一次计算到核查关闭全流程；参数和证据可追溯 | 重跑不重复、失败有提示、权限正确、结果可复现 |
| C 服务与组合场景 | 义务月历、人员工作日、历史状态；上线 M01/M02 | 两个场景、简版一户一档、指标与核查效果看板 | 正常/异常/缺失/复业/零记录样本均能解释，试点核查可接受 |
| D 扩展“6+1” | 按数据就绪接订单、检查、案件 | 每个场景独立口径、回放结果和人工验收，再关联展示 | 数据来源、对象匹配、历史时点和处置责任明确 |
| E 语义与学习增强 | 文本抽取、语义冲突及排序实验 | 与规则基线的对照结果、原文证据、误差分析 | 证明核查效率或准确性改善后才扩大使用 |

不预设全部阶段的工期。阶段 A 完成后，依据数据历史完整性、同步机制、业务确认与现有接口复用程度估算开发工作量。每阶段先最小样本验证，批量回算与大范围测试另行安排。

近期建议优先顺序：口径确认 → 指标目录及版本 → 拜访异常和户名预警的最小闭环 → 服务义务月历与缺访场景 → 看板和一户一档 → 其他领域模型。

## 十二、建议替换原文“一期最终应达到的效果”的表述

以现有营销审计及营销专卖查询为基础，统一拜访、客户服务和主体信息核对的指标口径，建立可追溯的指标目录、参数版本和数据质量检查机制。优先开展拜访履职异常、客户服务覆盖异常场景试点，形成预警生成、证据穿透、人工核查、整改复核及结果反馈的最小闭环。通过小范围运行和人工核查逐步完善规则与阈值，按数据就绪程度扩展经营状态、订货行为、专卖检查和案件一致性场景，并为后续语义分析及数据驱动模型保留规范的数据和评估基础。
